3. Estrutura de pastas do repositório (template)

Layout recomendado

/ ├── src/ │ ├── datasets/ # PBIP dos modelos semânticos (.Dataset) │ │ └── Vendas.Dataset/ │ ├── reports/ # PBIP dos relatórios (.Report) │ │ └── Vendas.Report/ │ ├── dataflows/ # Dataflow Gen2 (def. JSON/TMDL) │ ├── shared/ # Medidas e tabelas compartilhadas │ │ ├── calendar.tmdl │ │ └── fx-rates.tmdl │ └── pipelines/ # Data pipelines (Fabric/ADF) ├── docs/ │ ├── architecture.md # Desenho de arquitetura │ ├── naming-conventions.md │ ├── data-dictionary.md │ └── ★ adf / diagrams ├── tests/ │ ├── dax/ # DAX smoke tests (DAX Studio + json) │ ├── data-quality/ # Great Expectations / Soda │ └── sample-queries.json ├── deploy/ │ ├── dev/ # Workspace Dev — service principal A │ ├── test/ # Workspace Test — service principal B │ └── prod/ # Workspace Prod — service principal C (governado) ├── scripts/ │ ├── extract-pbip.ps1 │ ├── compile-pbip.ps1 │ ├── publish.ps1 │ └── refresh.ps1 ├── .github/workflows/ # ou azure-pipelines.yml │ └── bi-ci-cd.yml ├── .gitignore # Ignora .pbix, .pbit, bin/, obj/ ├── .gitattributes # LFS opcional p/ arquivos grandes ├── README.md └── CHANGELOG.md

Decisões de arquitetura

PBIP em vez de PBIX. O PBIX é binário e bloqueia versionamento granular. O PBIP é uma pasta de arquivos texto (TMDL + report.json + definition.pbir), permitindo diffs legíveis e PRs revisáveis.

Separação Dataset/Report. Camadas do modelo semântico e do visual ficam desacopladas. Vários reports podem consumir o mesmo dataset. Publicação independente.

Shared como biblioteca. Medidas, tabelas de calendário e funções de cálculo ficam em src/shared/ e são referenciadas pelos datasets — evita duplicação e facilita governança.

Três ambientes espelhados. A pasta deploy/ espelha os workspaces do Service. Cada um tem service principal próprio, com permissões mínimas (princípio do menor privilégio).

Testes antes do deploy. Smoke tests de DAX validam expressões-chave. Testes de qualidade de dados validam o ETL antes de publicar.

Boas práticas de governança

Service Principal por ambiente. Um para Dev, um para Test, um para Prod. Rotação trimestral via Azure Key Vault.

RLS versionado no TMDL. Roles e regras de segurança ficam no modelo, auditáveis no Git.

Conventional Commits. feat:, fix:, perf:, chore: — facilita changelog automático.

Branch policy. Mínimo 1 reviewer, build verde, sem merge direto em main.

Documentação obrigatória. Toda nova medida tem comentário TMDL + entrada no data-dictionary.md.

11. Multi-projeto · Escala do portfolio

A arquitetura é adaptativa a múltiplos BIs. Você não recria tudo a cada novo projeto — usa este scaffolding como Template Repo e escolhe 1 dos 3 padrões abaixo.

① Monorepo

Tudo num único repositório. Cada BI é uma pasta (vendas/, estoque/, rh/).

✅ Pipeline único, PRs cruzados, padrão único
❌ Cresce muito, CI roda tudo, sem acesso granular

1–5 projetos

② Template + Polyrepo ⭐

Este scaffolding vira Template Repo. Cada novo BI é um Use this template → repo independente.

✅ Isolamento total, CI leve, acesso granular
❌ Padrões podem divergir (mitigado por auditoria)

5–15 projetos

③ Federado ⭐⭐

Template + bi-shared-library central (TMDL, scripts, CI/CD). Projetos consomem via submodule.

✅ Padrão único versionado, fix de bug propaga em 1 PR
❌ Setup inicial mais elaborado

15+ projetos

🧬 Validação de DAX (AI sempre erra)

6 camadas de validação rodam antes de aceitar DAX do AI:

1. Sintaxe — pbi-tools compile

2. Semântica — executa em sandbox

3. Performance — cost estimate < 5s

4. Escopo — refs dentro do permitido

5. RLS — não vaza com RLS ativo

6. Naming — segue convenção

Falha em uma? Auto-correção (até 3x). Falhou todas? Reporta pro dev.

"isso, isso, isso"

🛑 Cenário 9 · Quando o AI sabe que não dá (alucinação evitada)

AI tenta gerar "Churn Risk Score" baseado em RFM. Falha 3x: perf ruim, ref inválida, RLS leak. Em vez de tentar 4ª vez, AI para e diz:

"3 tentativas esgotadas. Recomendo abordagem diferente:
pré-calcular RFM em Power Query (ETL) e ler via DAX simples.
Quer que eu (a) documente a análise, (b) tente outra abordagem,
ou (c) sugira um expert humano?"

Design intencional: AI sabe quando parar e escalar pra humano. É feature, não bug.

Subir o MCP server local

cd mcp/powerbi-mcp-server
pip install -e ".[dev]"

# editar .env

Bootstrap da infra Azure

./scripts/bootstrap/bootstrap-mcp-infra.ps1 `
  -SubscriptionId "xxx" `
  -ResourceGroupName "rg-bi-mcp-dev" `
  -Environment "dev"

Extrair dataset do Power BI

export PBI_TENANT_ID=xxx
export PBI_SP_CLIENT_ID=xxx
export PBI_SP_CLIENT_SECRET=xxx
python scripts/extract/extract_from_powerbi.py \
  --workspace "bi-vendas-prod" \
  --dataset "Vendas.Dataset" \
  --generate-docs --git-commit

Usar o ORM no Python

from powerbi_orm import Dataset, Measure, DAXExpression

ds = Dataset.connect(workspace="bi-vendas-dev", ...)
ds.tables["f_vendas__pedido"].add_measure(
    Measure(name="Vendas.Ticket Médio [R$]",
            expression=DAXExpression("DIVIDE(...)"))
)
ds.commit(branch="feat/ticket",
          message="feat: ticket médio",
          create_pr=True)
